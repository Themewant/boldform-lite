BoldForm Lite — Developer Guide

Extend, customize, and integrate with BoldForm using hooks, filters, and the plugin's architecture.

Applies to v1.1.1 · Updated 2026-06-24

BoldForm Lite is designed with extensibility in mind. Every major operation — rendering, saving, validation, email — passes through WordPress filters and actions. This guide covers the public API surface available to developers.

Architecture

Plugin Bootstrap

The plugin initializes on plugins_loaded via a singleton pattern:

// boldform-lite.php
function boldform_lite() {
    return BoldForm_Lite::get_instance();
}
add_action( 'plugins_loaded', 'boldform_lite' );

Freemium Architecture & Extensions

BoldForm Lite is built as the free tier of a freemium product. BoldForm Pro and third-party extensions hook into Lite without modifying its code. All extension points fire on the plugins_loaded hook via boldform_loaded, which passes the singleton instance:

add_action( 'boldform_loaded', function( $plugin ) {
    // $plugin is the BoldForm_Lite singleton
    // Register your hooks, actions, filters here
    add_filter( 'boldform_allowed_field_types', function( $types ) {
        $types[] = 'my_custom_field';
        return $types;
    } );
}, 10, 1 );

Important: This is the canonical bootstrap hook for all extensions. It runs after BoldForm's own hooks are in place, ensuring a stable foundation for your customizations.

BoldForm Pro — Architecture & Extension Model PRO

Pro is a separate plugin that extends Lite via the `boldform_loaded` hook and the module system. This section explains how Pro works and how it fits the freemium contract.

Pro Module System

Pro boots on Lite's boldform_loaded action (after a min-Lite-version compatibility check). On boot it instantiates each feature module into a registry, then — for every module whose is_enabled() returns true — calls register_hooks(), passing a shared BoldForm_Pro_Loader. Each module implements:

interface BoldForm_Pro_Module_Interface {
    // True when the license is valid AND this module's toggle is on.
    public function is_enabled();

    // Register this module's WordPress hooks via the shared loader.
    public function register_hooks( BoldForm_Pro_Loader $loader );
}

// Example: the Payments module plugs into Lite's seams.
class BoldForm_Pro_Payments implements BoldForm_Pro_Module_Interface {
    public function is_enabled() { /* license + 'payments' toggle */ }
    public function register_hooks( BoldForm_Pro_Loader $loader ) {
        $loader->add_filter( 'boldform_allowed_field_types', $this, 'register_field_types' );
        $loader->add_filter( 'boldform_field_control_html', $this, 'render_product_field', 10, 4 );
        $loader->add_filter( 'boldform_entry_data', $this, 'calculate_totals', 10, 3 );
    }
}

Modules are wired up in load_modules() (includes/class-boldform-pro.php); the Scheduling module boots slightly earlier via BoldForm_Pro_Scheduling::boot() so it can gate form output before render.

Pro Modules (13)

Pro ships its features as self-contained modules, each registering its own fields and hooks:

  • Multi-Page — page_break field, progress bar, step navigation
  • Payments — product, quantity, custom_amount, order_summary fields + PayPal & Stripe gateways
  • Analytics — view counts, conversion rate, field-abandonment tracking
  • Auto-Populate — extended pre-fill sources (user meta, post meta, query vars)
  • Webhooks — POST submissions to external HTTP endpoints
  • Calculation — calculation field (live formula evaluation)
  • Image Choice — image_choice field (image-based radio/checkbox)
  • Repeater — repeater field (add/remove row groups dynamically)
  • Signature — signature field (canvas-based signature pad)
  • Hidden Field — hidden_field with server-side resolved sources
  • Integrations — many third-party services (ActiveCampaign, ConvertKit, HubSpot, Google Sheets, Slack, Zapier, Make, and more)
  • Advanced Fields — password, rich_text, date_range, nps, matrix, lookup, geolocation
  • Scheduling — open/close dates, time windows, per-user submission limits

How Pro Extends Lite (No Code Duplication)

Critical principle: Pro does NOT copy or duplicate Lite code. Instead:

  1. Pro registers field types via `boldform_allowed_field_types` filter
  2. Pro renders fields via `boldform_field_control_html` filter (Lite's rendering engine)
  3. Pro validates fields via `boldform_validate_field` filter
  4. Pro formats field display via `boldform_format_field_value` filter
  5. Pro hooks into submission via `boldform_entry_created`, `boldform_entry_data`, etc.

This means: Lite owns the core form engine; Pro plugs into it without modifying Lite's code.

Pro JavaScript Events

Pro modules re-initialize on these frontend events (see JavaScript Events & Extension Guide for the full picture of which are fired by Lite vs. Pro):

  • boldform_frontend_init Pro — convention signal (fired by Pro / 3rd-party) to initialize Pro widgets; not fired by Lite
  • boldform_step_loaded Pro — fired by the Pro multi-page module to re-init calculation/repeater on a new step
  • boldform_form_reset — fired by Lite after a successful submission; Pro listens to clean up its state

Submission Flow Hooks

The submission lifecycle in order:

  1. boldform_gate_submission — accept or reject before validation
  2. boldform_before_submission — fires before field validation
  3. boldform_submission_request — modify raw request payload
  4. boldform_entry_data — mutate validated entry data
  5. boldform_should_save_entry — control whether entry is persisted
  6. boldform_before_entry_save — last chance before DB insert
  7. boldform_entry_saved — after entry inserted
  8. boldform_entry_created — entry ID available, triggers integrations
  9. boldform_submission_result — filter the final JSON response

boldform_gate_submission

Reject an entire submission before validation. Return an array with 'success' => false (and an optional 'message') to block it; the default value passed in is null.

add_filter( 'boldform_gate_submission', function( $gate, $form_id, $settings, $request ) {
    if ( ! is_user_logged_in() ) {
        return array( 'success' => false, 'message' => 'Please log in to submit this form.' );
    }
    return $gate;
}, 10, 4 );

boldform_entry_data

Modify entry data after validation, before saving.

add_filter( 'boldform_entry_data', function( $data, $form_id, $settings ) {
    $data['submitted_url'] = sanitize_url( wp_get_referer() );
    return $data;
}, 10, 3 );

boldform_should_save_entry

Return false to skip saving the entry to the database.

add_filter( 'boldform_should_save_entry', function( $should_save, $form_id, $entry_data, $settings, $request ) {
    // Don't save entries for a specific form
    if ( 42 === $form_id ) {
        return false;
    }
    return $should_save;
}, 10, 5 );

The admin email is sent to the site owner. Filter its subject and HTML body. Both filters receive the form record object ($form_record, not an ID) and the sanitized entry data.

';

The user confirmation email is sent to the address auto-detected from an email field in the submission. Its filters receive a fourth argument, $user_email (the detected recipient).

Adding a Field Type (Step by Step)

  1. Register in field library via boldform_field_library
  2. Whitelist for save via boldform_allowed_field_types
  3. Render on frontend via boldform_field_control_html
  4. Save extra properties via boldform_field_extra_keys (optional)
  5. Add builder JS data via boldform_builder_localize_data (optional)
  6. Add builder preview via inline script (optional)

Minimal Example

<?php
// 1. Add to field library
add_filter( 'boldform_field_library', function( $lib ) {
    $lib['color_picker'] = array(
        'label' => 'Color Picker',
        'icon'  => 'dashicons-art',
        'group' => 'advanced',
    );
    return $lib;
} );

// 2. Allow saving
add_filter( 'boldform_allowed_field_types', function( $types ) {
    $types[] = 'color_picker';
    return $types;
} );

// 3. Render on frontend
add_filter( 'boldform_field_control_html', function( $html, $type, $name, $field ) {
    if ( 'color_picker' !== $type ) return $html;

    $default = esc_attr( $field['default_value'] ?? '#000000' );
    $req     = ! empty( $field['required'] ) ? ' required' : '';

    return '<input type="color" id="' . esc_attr( $name ) . '" name="' . esc_attr( $name ) . '" value="' . $default . '"' . $req . '>';
}, 10, 4 );

Custom Validation

BoldForm provides multiple validation hooks for different scopes:

Per-Field Validation

Use boldform_validate_field to validate a single field before the entry is saved. The filter receives ($error, $value, $field, $request) — the field's id and type are on the $field array. Return a non-empty string (the error message) to fail validation; return the unchanged $error (empty by default) to pass.

add_filter( 'boldform_validate_field', function( $error, $value, $field, $request ) {
    if ( 'number' === ( $field['type'] ?? '' ) && 'age' === ( $field['id'] ?? '' ) ) {
        if ( absint( $value ) < 18 ) {
            return 'You must be 18 or older.';
        }
    }
    return $error;
}, 10, 4 );

Form-Level & Entry Data Validation

Use boldform_gate_submission for form-level checks (reject the whole submission), or boldform_entry_data to mutate validated data before save:

add_filter( 'boldform_gate_submission', function( $gate, $form_id, $settings, $request ) {
    if ( 5 === $form_id ) {
        $age = absint( $request['boldform_age'] ?? 0 );
        if ( $age < 18 ) {
            return array( 'success' => false, 'message' => 'You must be 18 or older.' );
        }
    }
    return $gate;
}, 10, 4 );

End-to-End Add-On Tutorial: Custom Validation Field

Build a complete, shippable add-on that adds a custom "Phone" field with validation and formatting.

Step 1: Register the Field Type

add_filter( 'boldform_field_library', function( $library ) {
    $library['phone'] = array(
        'label'  => 'Phone (US)',
        'icon'   => 'dashicons-phone',
        'group'  => 'basic',
        'pro'    => false,
    );
    return $library;
} );

Step 2: Whitelist the Field for Save

add_filter( 'boldform_allowed_field_types', function( $types ) {
    $types[] = 'phone';
    return $types;
} );

Step 3: Render on Frontend

add_filter( 'boldform_field_control_html', function( $html, $type, $field_name, $field ) {
    if ( 'phone' !== $type ) {
        return $html;
    }

    $value = isset( $_POST[ $field_name ] ) ? sanitize_text_field( $_POST[ $field_name ] ) : '';
    $required = ! empty( $field['required'] ) ? ' required' : '';

    return '<input type="tel" id="' . esc_attr( $field_name ) . '" name="' . esc_attr( $field_name ) . '" value="' . esc_attr( $value ) . '" pattern="[0-9\-\(\)\s]+"' . $required . ' placeholder="(123) 456-7890">';
}, 10, 4 );

Step 4: Add Validation

The filter receives ($error, $value, $field, $request); return a non-empty string to fail.

add_filter( 'boldform_validate_field', function( $error, $value, $field, $request ) {
    if ( 'phone' !== ( $field['type'] ?? '' ) ) {
        return $error;
    }

    // Remove non-digits for validation
    $digits_only = preg_replace( '/[^\d]/', '', $value );

    // US phone: 10 digits
    if ( strlen( $digits_only ) !== 10 ) {
        return 'Please enter a valid 10-digit US phone number.';
    }

    return $error;
}, 10, 4 );

Step 5: Format for Display

add_filter( 'boldform_format_field_value', function( $formatted, $value, $field_type ) {
    if ( 'phone' !== $field_type ) {
        return $formatted;
    }

    // Format: (123) 456-7890
    $digits = preg_replace( '/[^\d]/', '', $value );
    if ( strlen( $digits ) === 10 ) {
        return sprintf( '(%s) %s-%s', substr( $digits, 0, 3 ), substr( $digits, 3, 3 ), substr( $digits, 6 ) );
    }

    return $value;
}, 10, 3 );

Step 6: Display in Admin Entries List

add_filter( 'boldform_entry_value_admin_html', function( $html, $value, $field_type, $field ) {
    if ( 'phone' !== $field_type ) {
        return $html;
    }

    $digits = preg_replace( '/[^\d]/', '', $value );
    $formatted = strlen( $digits ) === 10 ? sprintf( '(%s) %s-%s', substr( $digits, 0, 3 ), substr( $digits, 3, 3 ), substr( $digits, 6 ) ) : $value;

    return '<a href="tel:' . esc_attr( $value ) . '">' . esc_html( $formatted ) . '</a>';
}, 10, 4 );

Result: You now have a complete phone field add-on with field registration, validation, formatting, and admin display. Ship this as a standalone plugin or include it in a larger extension.

Hook Stability & Deprecation Policy

All hooks listed in the Hook Reference Table are part of BoldForm's public API and are stable.

Stability Guarantee

  • Shipped hooks never disappear. If a hook is released, it remains available in all future releases.
  • Hook signatures don't change. The number and order of parameters are fixed; new parameters are added only at the end (for filters) or as new hooks.
  • Hook behavior is predictable. The timing and context of hook execution don't change between versions.

Deprecation Process

If a hook must be retired (very rare), the deprecation follows this process:

  1. Notice Phase (1 minor version): The hook is marked deprecated in the codebase; a `_deprecated_hook()` call alerts developers via WordPress debug logs.
  2. Grace Period (1 major version): The hook still fires and works normally, but deprecation notices are logged.
  3. Removal: The hook is removed in the next major version (e.g., v2.0.0).

@since Markers

Every hook in the Hook Reference Table includes a @since version (e.g., "1.0.0", "1.1.0"). This tells developers which version introduced the hook. If you depend on a hook added in v1.1.0, you can safely assume it exists in v1.1.0+.

Third-Party Extensions

If you ship an extension (plugin, theme, or SaaS integration) that uses BoldForm hooks:

  • Target a minimum version. Document which version of BoldForm your extension requires.
  • Check for hook existence. Use has_filter() or has_action() before calling dynamic hooks.
  • Use @since markers as a reference. Don't use hooks released after your stated minimum version.

JavaScript Events & Extension Guide

BoldForm Lite's frontend fires a single jQuery event that extensions can hook into. Two additional events listed below are a shared convention used by BoldForm Pro modules — Lite itself does not fire them, but documenting them here lets you write one extension that works in both Lite and Pro forms.

EventFired byTargetDetail / Use
boldform_form_resetLite (frontend)documentFired after a successful AJAX submission and form reset; args [ $form ]. Use to clean up custom state.
boldform:form_settings_renderedLite (builder)documentformSettings object — fired when the Settings panel renders; used to inject Pro setting tabs. Builder only.
boldform:before_saveLite (builder)documentformSettings object — builder only; attach handlers to inject extra keys before save.
boldform_frontend_init ProPro / 3rd‑partydocumentConvention signal that a form was (re)injected into the DOM. Pro field modules listen to (re)initialize widgets. Not fired by Lite.
boldform_step_loaded ProPro (multi‑page)documentConvention signal that a multi-step form advanced to a new page. Fired by the Pro multi-page module, not by Lite.

Hooking into the Lite reset event

In a Lite-only install, the event you can rely on is boldform_form_reset, fired on document after a successful submission:

jQuery( document ).on( 'boldform_form_reset', function( e, $form ) {
    // $form is the jQuery-wrapped form element. Clean up custom widget state here.
    MyWidget.cleanup( $form );
} );

Writing an extension that also works on Pro forms

If your widget needs to (re)initialize when Pro injects or re-renders a form (e.g. multi-step navigation or repeater rows), also listen for the Pro convention events. They are harmless in a Lite-only install — they simply never fire:

// Runs on initial load and again whenever Pro (re)injects / advances the form.
jQuery( document ).on( 'boldform_frontend_init boldform_step_loaded', function( e, formEl ) {
    var $form = jQuery( formEl );
    MyWidget.init( $form );
} );

The Double-Bind Guard Pattern

Because the convention re-init events (boldform_frontend_init / boldform_step_loaded) can fire more than once for the same form, guard your initializer so it only runs once per form element:

jQuery( document ).on( 'boldform_frontend_init', function( e, formEl ) {
    var $form = jQuery( formEl );
    // Check if already initialized
    if ( $form.data( 'mywidget_initialized' ) ) {
        return; // Skip if already done
    }

    // Initialize the widget
    MyWidget.init( $form );

    // Mark as initialized
    $form.data( 'mywidget_initialized', true );
} );
